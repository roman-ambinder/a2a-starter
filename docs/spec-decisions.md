# Spec decisions

This SDK follows A2A v1.0.1 (proto pinned to tag `v1.0.1`, see [proto/README.md](../proto/README.md)). Where the spec leaves a choice open, this page records the choice and the reason. Section numbers are from the v1.0.1 specification.

| Topic | Spec | Choice | Reason |
|---|---|---|---|
| Patch in `A2A-Version` | §3.6 | The header is trimmed (`" 1.0 "` is accepted). `1.0.1` is accepted as `1.0`. A leading `v` (`v1.0`) is not accepted. Anything that is not `Major.Minor` or `Major.Minor.Patch` is unsupported. | The spec says patch must not be used in negotiation. Rejecting it would break clients that send the full version. |
| Empty `A2A-Version` | §3.6.2 | Treated as 0.3. The server does not serve 0.3, so it answers `VersionNotSupported`, with a message that says to send `A2A-Version: 1.0`. | The spec makes empty mean 0.3. 0.3 support is planned as a separate package. |
| `supportedVersions` in errors | §3.3.2, §6.4 | `VersionNotSupported` carries ErrorInfo metadata `supportedVersions` = `"1.0"` (comma-separated). | ErrorInfo metadata values are strings. |
| Client interface selection | §3.6, §8.3.2 | The client takes the first card interface (or the preferred binding) whose binding is supported and whose `protocolVersion` Major.Minor is `1.0`. An empty `protocolVersion` is taken as `1.0`. | The field is required, but some cards omit it; skipping them would leave no usable interface. |
| Unknown enum values | §5.5, §5.7 | An unknown enum name or number reads as `*_UNSPECIFIED` instead of failing the payload. A known integer is accepted. Output is always the ProtoJSON name. | Same result as a protobuf parser that ignores unknown values; a newer peer must not break an older reader. An unknown `TaskState` therefore reads as `Unspecified` on the client: it is neither terminal nor interrupted. The server rejects `ROLE_UNSPECIFIED` on a message ("use ROLE_USER"), so 0.3 values like `"user"` still fail with a clear error. An unknown `ListTasks` status filter means "no filter", as in proto3. |
| JSON-RPC `error.data` | §9.5 | An array of `@type`-tagged details. A2A errors carry one `google.rpc.ErrorInfo` (reason, domain `a2a-protocol.org`, metadata). Standard JSON-RPC errors (-32700 to -32603) carry no `data`, except the server-generated internal error (see "Internal error trace id"). | 9.5 defines `data` as a detail array; 3.3.2 requires ErrorInfo for A2A errors. |
| Internal error trace id | §3.3.2 | An unknown exception on the server becomes `InternalError` with a generic message that names a trace id. It carries one `google.rpc.ErrorInfo` with reason `INTERNAL`, domain `a2a-protocol.org` and metadata `traceId`, on all three transports. Only server-generated internal errors get this. An `InternalError` a handler throws keeps its data off the wire. The client keeps the metadata of an ErrorInfo with an unknown reason in `A2AException.Data` and `Details`. | `InternalError` has no catalog reason. The trace id lets an operator find the logged exception without leaking it to the caller. |
| Client error mapping | §3.3.2 | On every transport the ErrorInfo reason selects the error code; ErrorInfo metadata becomes `A2AException.Details` (a map of strings; `Data` keeps the raw JSON object). A JSON-RPC `data` that is not a detail array is kept as is. | One error model on all transports; older servers still work. |
| Extended card not offered | §3.3.4 | `capabilities.extendedAgentCard` not true: `UnsupportedOperation`, for every caller. The check runs before extended-card authentication, but after the agent's own authorization policy: an anonymous caller of a policy-protected agent gets 401. Declared but not configured: `ExtendedAgentCardNotConfigured`. When the capability is on, the caller must be authenticated. | Exactly as 3.3.4 says. A card that does not offer the card has nothing to protect, so an anonymous caller gets the clear error, not an auth failure. |
| Required extensions | §3.3.4, §4.6.3 | Checked on every operation of the agent (not only SendMessage), on all transports. The card endpoint is not an operation and is not checked. | 3.3.4 does not limit the rule to one operation. |
| Extension echo | §3.2.6 | Activated extensions (requested and declared on the card) are sent back in `A2A-Extensions` (HTTP) or `a2a-extensions` response metadata (gRPC). No header when none is activated. | Lets the client see what the agent applied. |
| `contextId` limits | §3.4.1 | A client `contextId` is kept as given. It is rejected (`InvalidParams`) when it is longer than 256 characters or has control characters. It is never replaced. | The spec lets the server reject ids it cannot accept, and forbids silently replacing them. |
| Tenant | §8.3.2 | The client sends the selected interface's `tenant` on every request. A request with a different non-empty tenant throws `ArgumentException` before anything is sent. Without an interface tenant the request value is sent as given. | The spec says the request tenant must equal the interface tenant. |
| gRPC interface URL | §8.3.1, §8.5 | The server writes `host:port` for gRPC interfaces. The client accepts `host:port` (TLS unless the host is loopback; `A2AClientOptions.GrpcUseTls` overrides) and full `http://` / `https://` URLs. | The spec does not say what form a gRPC `url` takes (its §8.5 sample card uses an `https://` URL). Other SDKs and the TCK use the value as a channel target, so we write `host:port` and read both forms. |
| Card caching | §8.6.1 | Card responses send `Cache-Control: public, max-age=300` (`A2AServerOptions.CardCacheMaxAge`; zero sends `no-cache`), `Vary: A2A-Version`, and a strong `ETag` (see "Card ETag source"). `If-None-Match` gets 304. The extended card sends `Cache-Control: private, no-store` on REST and JSON-RPC (gRPC has no HTTP cache header). | The hash is the same on every instance, so a load balancer does not break conditional requests. The extended card is per caller. |
| Deprecated OAuth flows | §4.5.7 | `implicit` and `password` flows are modeled and round-trip through JSON and proto. The client never uses them to get tokens. The types and the `OAuthFlows.Implicit` / `Password` properties are `[Obsolete]` ("Removed from OAuth 2.1; kept so cards round-trip."); our own mapper, serializers and round-trip tests suppress CS0618 on purpose. A consumer that lists the flow types in its own `JsonSerializerContext` must suppress CS0618 the same way. | Cards from other agents must not lose data. |
| Inbound JSON-RPC content type | §9.1 | The server answers `application/json`. It also accepts requests sent as `application/a2a+json`. | Tolerant inbound: other SDKs send it. |
| JSON-RPC param names | §5.5, §9 | `snake_case` params (for example `task_id`) are not accepted today; only the camelCase ProtoJSON names. A later, separate change may add this. | Owner decision 2026-11-03. The TCK sends `snake_case` on JSON-RPC; see `a2aproject/a2a-tck` issues 242 and 264. |
| JSON-RPC batch | §9 | Rejected with `InvalidRequest`. | JSON-RPC batches are not part of A2A. |
| SSE resume | §3.5.2 | Not supported (`Last-Event-ID` is ignored). | Not defined by the spec (open issue #1635). |
| When streams close | §3.1.2, §3.1.6, §11.7 | A `SendStreamingMessage` stream closes at a terminal or interrupted state (`INPUT_REQUIRED`, `AUTH_REQUIRED`). A `SubscribeToTask` stream stays open through interrupted states and closes only at a terminal state. | 11.7 closes streams at interrupted states, but 3.1.6 allows subscribing to any non-terminal task and ends that stream at a terminal state. Closing at once would make subscribing to a waiting task useless. A `SubscribeToTask` stream on a waiting task stays open until the task ends or the client disconnects. There is no server idle limit yet. |
| Server tenant check | §8.3.2 | `A2AServerOptions.InterfaceTenants` (agent name to tenant) puts `tenant` on every interface of that agent's card. A request that names a different tenant gets `InvalidParams`: "tenant 't2' does not match this interface (tenant 't1'). Leave tenant empty or send 't1'." An empty request tenant is filled with the interface tenant. Agents without an entry accept any tenant. Requests handed to an `IA2AVersionDispatcher` keep their own rule (`A2AVersionDispatchContext.Tenant`). | The spec says the request tenant must equal the interface tenant, and the spec does not say where a server gets it. Package 07 replaces this option with `A2ASecurityOptions.Tenants`. |
| Card ETag source | §8.6.1 | The ETag is `"` + base64url(first 16 bytes of SHA-256(payload, then `0x0A` and the UTF-8 `kid` for each signature in ordinal order)) + `"`. `payload` is the served card JSON without `signatures`. The `kid` comes from the signature's protected header, else its `header`. | Re-signing with the same keys keeps the ETag, and the value is the same on every instance. `payload` is the plain serialization for now. Package 04 swaps in the RFC 8785 form; the hash rule stays. |
| Card contributors | §3.1.11, §8.6.1 | `IAgentCardContributor` runs on the public card endpoints only. `AgentCardContext.IsExtended` is always false. | The extended card is returned as a model on all three transports (proto on gRPC), so JSON additions cannot reach it the same way everywhere. |
| Request Content-Type | §3.2.1 | The server is lenient on the request `Content-Type` header on purpose. It does not answer 415 or `ContentTypeNotSupported` for it. `ContentTypeNotSupported` is used for part media types. | Tolerant inbound: clients often send `application/json` or nothing. As a result the TCK tests for it skip (`HTTP_JSON-STATUS-001`, JSON-RPC wrong content type). |
| Version dispatch | §3.6 | For JSON-RPC and REST the order is: read `A2A-Version`, resolve the caller and tenant (an auth failure ends the request here for every version; an empty request tenant is filled with the agent's interface tenant, and a different one fails with `InvalidParams`, so the dispatcher never sees it; JSON-RPC has no request tenant at this point and gets the interface tenant), then, when the version is not one the core serves, ask the registered `IA2AVersionDispatcher` instances. The first that claims the version handles the whole request. The body (or REST operation) is read after that, and only for a supported version. Otherwise the request gets `VersionNotSupported`. | A dispatcher (for example a 0.3 package) must not skip authentication, and must see the raw request. The dispatcher types are internal until package 07 lands. |
| Task state transitions | §4.1.3 | The table in [spec 03, D13](superpowers/specs/2026-11-03-sdk-03-spec-conformance-design.md). A new task is SUBMITTED. From SUBMITTED or WORKING the agent may move to WORKING, INPUT_REQUIRED, AUTH_REQUIRED, COMPLETED, FAILED, REJECTED or CANCELED (never SUBMITTED). From INPUT_REQUIRED or AUTH_REQUIRED only the server moves the task: SUBMITTED or WORKING for a continuation, CANCELED for a cancel request. Terminal states never change. An illegal move throws `InvalidAgentResponse` and the task ends FAILED. A cancel of a CANCELED task returns it; a cancel of another terminal task gives `TaskNotCancelable`. | The spec names the states but gives no transition table. These rows follow its lifecycle and its definition of interrupted and terminal states. |
| Cancel handler moves | §3.1.5, §4.1.3 | The event sink given to `IAgentHandler.CancelAsync` allows only CANCELED. Any other move is rejected with `InvalidAgentResponse`. On a paused task the cancel request still ends the task CANCELED. On a SUBMITTED or WORKING task the task ends FAILED and the cancel call answers `TaskNotCancelable`. | A paused task must stay cancelable whatever the handler does. On a running task the D13 rule applies as for any agent. |

## Checking conformance

`tests/Ambinder.A2A.Tck.Sut` is a small server for the official [A2A TCK](https://github.com/a2aproject/a2a-tck). It serves all three transports and the behaviors in the TCK's `scenarios/` files. It keeps the extended card off, because the TCK cannot send credentials and the library requires authentication when the capability is on. With the capability off, the TCK skips those tests.

The TCK is pinned by commit in `tck/TCK_VERSION`. CI runs it on every PR (job `tck`, `.github/workflows/tck.yml`). To run the same steps locally (build and start the SUT, check out the TCK, run it once per transport, check the reports):

```
mkdir -p /tmp/a2a-tck-run
RUNNER_TEMP=/tmp/a2a-tck-run bash tck/run-ci.sh
```

The script runs this loop in the TCK checkout, then calls the checker:

```
for t in jsonrpc http_json grpc; do
  rm -rf reports
  uv run ./run_tck.py --sut-host http://localhost:9999 --transport "$t" || true
  mkdir -p "tck-reports/$t" && cp -r reports/. "tck-reports/$t/"   # reports are overwritten on each run
done
```

Reports and `checker-output.txt` are left in `tck-reports/`, the SUT log in `$RUNNER_TEMP/sut.log`. The exit code is the checker's. See [tck/README.md](../tck/README.md) for the rules.

Do not pass `--level should` to the TCK: it runs only SHOULD tests and skips every MUST. The checker grades each requirement by its own level.

The TCK reads the card at `{sut-host}/.well-known/agent-card.json` and tests every interface on it. A known TCK bug goes on the list in `tck/known-issues.json`. A `MUST` entry is allowed only for a proven TCK bug: it has `level: "MUST"`, `kind: "tck-bug"`, the spec text in `spec`, an upstream issue link and an expiry date. Our own MUST failures are never listed. Each entry links its upstream issue and expires on 2027-02-02; renew it only while the bug is still open upstream.

Entries marked **implementer default** are my choice, as the least lossy one, and wait for owner review; none of them is final.

**Mapping choices**

- **`blocking`** (`SendMessageConfiguration`): `ReturnImmediately = !blocking`; the vendored files state no default for an absent `blocking` (inventory `blockingDefaultStatedInFiles: false`, closed in the row "`blocking` default" above). **Implementer default:** an absent `blocking`, and an absent `configuration`, read as `false`, so `ReturnImmediately = true`. Going out, `blocking` is always written (`!ReturnImmediately`), so a 1.0 request without a configuration becomes `blocking: true`. Consequence: a 0.3 caller that omits `blocking` gets the task back at once instead of waiting; callers that want to wait must send `blocking: true`. The converter test is named `Blocking_absent_equals_false_so_return_immediately_is_true`.
- **File parts:** `bytes` is the base64 text in 0.3 and `Raw` bytes in 1.0 (invalid base64 gives `InvalidParams`); a file with both or neither of `bytes` and `uri` gives `InvalidParams`.
- **Timestamps:** read with the 1.0 rule (no offset means UTC); written as UTC with `Z`. An offset like `+02:00` is normalized to UTC, so the string can change while the instant does not. The Python captures in `tests/vectors` without an offset gain a `Z`.
- **Artifact update flags:** a missing `append` or `lastChunk` reads as `false`; both are always written on the way out, also when `false`.
- **Empty lists:** `extensions`, `referenceTaskIds`, `artifacts`, `history`, `acceptedOutputModes` that are empty in 1.0 are omitted in 0.3; absent in 0.3 reads as empty in 1.0.
- **Missing members at run time:** the 0.3 models do not apply their initializers to a member that is missing on the wire (for example `Message.MessageId`, `Parts`, `Task.Status` are `null` after reading `{}`). The converters accept that: missing `parts` read as empty, a missing `status` as an empty status, a missing `messageId` as `""`, and `message/send` params without `message` give `InvalidParams`. This is a Task 4 model quirk, not a Task 6 choice; fix it there if the models should be strict.

**Cards (decided in Task 7: `V03CardWriter`, `V03CardReader`)**

Writer (1.0 card to dual card; add-only, idempotent, never changes or removes an existing member):

- **Interfaces.** For each distinct (binding, url) of the 1.0 interfaces on JSON-RPC and REST (and `GRPC` only when the writer option `IncludeGrpc` is on, because `MapA2AGrpcV0_3` is opt-in), one entry is appended to `supportedInterfaces` with `protocolVersion: "0.3"` and the same URL. The 1.0 entries stay first and unchanged. Only Major.Minor is written (`0.3`); the full `AdvertisedVersion` (default `0.3.0`) goes in the legacy `protocolVersion`. `tenant` is copied to the added entry (0.3 has no tenant; 0.3 clients ignore it).
- **REST URL.** **Awaiting owner review (plan text, no source in the vendored files).** The REST 0.3 entry carries the same base URL as the 1.0 entry, as plan 15 and spec 15 say ("0.3 clients add `/v1`"). The vendored files do not say that (see the open row "`/v1` and the interface URL"): the 0.3 sample card lists a REST `url` without `/v1`, and 3.2.3 only says the method paths start with `/v1`. If the owner decides otherwise, the change is one line in `V03CardWriter`.
- **Legacy members** (only with `LegacyCardFields`, and only when at least one 0.3 interface exists; each is added only when the card JSON does not already have that member): `protocolVersion` = `AdvertisedVersion`; `url` and `preferredTransport` = the 0.3 JSON-RPC interface, else the first 0.3 interface (the transport written is that interface's, so the pair is always consistent); `additionalInterfaces` = **all** 0.3 interfaces as `{url, transport}`, including the main one, because the vendored spec says the list SHOULD include the main `url`/`preferredTransport` (spec 5.6, schema `additionalInterfaces`); plan 15 says "the other" interfaces, and the vendored text wins (**awaiting owner review**); `security` = `securityRequirements` as `[{scheme: [scopes]}]`, one entry per requirement, kept by name (an empty requirement stays `{}`); `supportsAuthenticatedExtendedCard` = `capabilities.extendedAgentCard` when it is declared (closes the open row "Card: fields spec 15 does not mention").
- **Members 0.3 requires and 1.0 omits (implementer default, awaiting owner review).** 1.0 serialization omits empty lists and an empty `capabilities`; with `LegacyCardFields` the writer adds `skills`, `defaultInputModes`, `defaultOutputModes` as `[]` and `capabilities` as `{}` when absent, so a 0.3 parser that requires them does not fail. A 1.0 parser reads them as empty.
- **Not bridged (same key, different shape, or nested):** `securitySchemes` is a 1.0 wrapper object (`{"bearer": {"httpAuthSecurityScheme": {...}}}`) and the key cannot hold the 0.3 flat form (`{"type": "http", ...}`), so a 0.3 client sees scheme names in `security` but cannot read the scheme definitions. Skill-level `securityRequirements` (0.3 `skills[].security`) and `capabilities.stateTransitionHistory` would be additions inside existing members, which the contributor rule (add only top-level members) forbids. 1.0 `AgentInterface.Tenant`, `OAuthFlows.DeviceCode` and `PkceRequired` have no 0.3 form. (A2A discussion #1416.)
- **Unknown members.** Our 1.0 parser (`A2AJson.AgentCard`, System.Text.Json defaults) skips unknown members, so `url`, `preferredTransport` and the rest do not break it; tests parse the dual card and compare it with the input.

Reader (0.3-only card JSON to 1.0 `AgentCard`; `TryRead` is `false` for a non-object, for any card with `supportedInterfaces` (1.0 and dual cards), and for a card without a string `url`):

- **Interfaces.** `url` + `preferredTransport` first, then `additionalInterfaces`, deduplicated by (url, transport), each at `protocolVersion: "0.3"` whatever the card's own `protocolVersion` (`0.3.0`, `0.2.9`, ...). An absent or empty `preferredTransport` or `transport` reads as `JSONRPC`. Transport strings are kept as they are (`JSONRPC`, `GRPC`, `HTTP+JSON`).
- **By name:** `name`, `description`, `version`, `documentationUrl`, `iconUrl`, `provider`, `defaultInputModes`, `defaultOutputModes`, `capabilities.streaming`, `capabilities.pushNotifications`, `capabilities.extensions` (`params` kept as JSON), skills (`id`, `name`, `description`, `tags`, `examples`, `inputModes`, `outputModes`), `signatures` (`protected`, `signature`, `header`).
- **`security` and `skills[].security`** become `securityRequirements`: each map entry is a scheme name with its scope list, one `SecurityRequirement` per array item.
- **`supportsAuthenticatedExtendedCard`** becomes `Capabilities.ExtendedAgentCard`.
- **`securitySchemes`** are converted from the flat form to the 1.0 wrappers (`apiKey` -> `ApiKeySecurityScheme` with `in` as `Location`; `http`; `oauth2`; `openIdConnect`; `mutualTLS`). A scheme with an unknown `type` is dropped. **Awaiting owner review (implementer default):** 1.0 `OAuthFlows` is a oneof but 0.3 allows several flows; the first present flow in the order authorizationCode, clientCredentials, implicit, password is kept and the others are dropped.
- **Dropped:** `protocolVersion` (the interfaces carry `0.3`), `capabilities.stateTransitionHistory`.
- **Errors.** A card that has `url` but wrong member types throws `JsonException`; it is not reported as `false`.
